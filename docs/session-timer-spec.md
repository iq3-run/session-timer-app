# セッションタイマーアプリ 開発仕様書（Claude Code引き継ぎ用）

## 1. 背景・目的

セミナー／教育プログラムの運営者が、セッションを時間どおりに終わらせるために使うタイムマネジメント用スマホアプリ。

- セッションは約1年にわたって開催され、大きな節目のセッションを「週末」と呼ぶ
- 運営中は少なくとも3〜4時間、画面を表示し続ける想定 → **電池消費を抑える設計が必須**
- これまでHTMLプロトタイプ（本仕様書と同梱の `session-timer.html`）で機能検証を行い、実際に使用した結果いくつかの改善点が見つかった
- HTMLではなく**ネイティブアプリとして開発**する（理由：後述の「完了時刻の永続化」など、ブラウザのプロトタイプでは実現できない要件があるため）

## 2. プロトタイプからの実装済み機能（そのまま踏襲）

- 単一画面構成（タブ切り替えなし）＋設定シート（⚙）
- 現在時刻を大きく表示（HH:MM:SS、端末のタイムゾーン＝日本なら自動的にJST）
- 「完了まで」カウントダウン（同じく大きく表示、現在時刻と同サイズ）
  - 完了時刻の表示部分をタップ→ネイティブの時刻ピッカーが直接開き、ダイアログを挟まず即設定できる
  - 設定済みの場合、右上の✕で解除
- 「指定時刻」カウントダウン（複数登録可、それぞれの残り時間を常時表示）
  - 「＋指定時刻を追加」をタップ→ネイティブピッカーが直接開き、続けてタイトル入力ダイアログ
    が開く（空欄可）。タイトル未入力なら従来通り「指定時刻 H:MM」表記、入力すればタイトルの
    文字列をそのまま冠した表記になる（例: タイトルが「朝礼」なら「朝礼 H:MM」）
  - 既存の行をタップ→ネイティブピッカーとタイトル入力ダイアログが開き直接変更、✕で削除
  - 指定時刻のフラッシュ・通知は、ちょうどその瞬間に加えて15/10/5/3/2/1分前にも発火する。
    タイトルがあれば「タイトルまで残り○分」「タイトルになりました」（例: 「朝礼まで残り5分」）、
    なければ従来通り「残り○分」「指定時刻になりました」という文言になる
- ストップウォッチ
  - 専用エリアをタップで開始／一時停止
  - 経過時間は1/10秒まで表示（他の表示は1秒間隔更新のまま、ストップウォッチのみ滑らかに更新し電池消費とのバランスを取る）
- 画面フラッシュ（完了◯分前に発火）＋端末通知＋バイブレーション
- おまけ：週末（マイルストーン）までの日数、週末間の日数、NTPによる時刻同期

## 3. 今回追加する要件（実使用フィードバック）

### 3-1. タイマー機能（新規）
ストップウォッチ／完了カウントダウンとは別に、単独のカウントダウンタイマーを追加する。

- タイマー設定時に、以下のどちらかを選べるようにする：
  1. **通常タイマー**：設定した瞬間からカウントダウン開始
  2. **ストップウォッチ連動タイマー**：ストップウォッチの「開始時刻」を基準にカウントダウンする
     - 例：ストップウォッチを開始してから3分後に「7分」のタイマーを連動モードで設定 → 設定した瞬間、タイマーはすでに3分経過している扱いになり、残り4分からスタートする

**タイマーの起動・リセットのジェスチャー仕様（確定）**：ストップウォッチとは異なり、シンプルに2種類のジェスチャーのみとする。**タップの挙動は稼働中かどうかに関わらず常に同じ**

| 状態 | タップ | 長押し |
|---|---|---|
| 未設定／稼働中（カウントダウン中・超過カウントアップ中）のいずれでも共通 | 時間＋モード選択の設定画面を開く。確定すると、その時間・モードで**新たにスタート**する（稼働中に確定した場合は、それまでのカウントダウンを置き換える形になる） | **完全リセット**（未設定状態に戻す） |

- **ダブルタップは使用しない**（ストップウォッチのダブルタップ＝リセット＋即リスタート、とは仕様が異なる点に注意）
- **一時停止機能は設けない**：通常タイマー・連動タイマーのどちらも、一度動き出したら一時停止できない設計とする。止める操作は「長押し（完全リセット）」のみ

- **連動タイマーとストップウォッチ操作の追従仕様**：
  - ストップウォッチの一時停止／再開 → タイマーはそのまま（一緒に止めたり動かしたりしない、独立してカウントを続ける）
  - ストップウォッチのリセット（長押し） → タイマーもリセットする
  - ストップウォッチのダブルタップ（リセット＋リスタート） → タイマーが完了（超過）していなければそのまま、すでに超過していればタイマーもリセットする
- **連動タイマー設定時にすでに過ぎているフラッシュポイントの扱い**：例のように設定時点ですでに「5分前」を過ぎているケースでは、その5分前フラッシュは発火させない（無視する）。まだ先のフラッシュポイント（例では3分前・1分前）はその瞬間になったタイミングで通常どおり発火する
- **タイマー開始時の自動連動**：タイマーをスタートさせた時点でストップウォッチが動作していなければ、ストップウォッチも自動的に開始する（タイマーとストップウォッチが同時に動き出す）。このルールは通常タイマー／連動タイマーどちらの開始でも、また後述の「+30秒/+1分の長押しによるクイックスタート」でも一律に適用する
- **「+30秒」「+1分」ボタン**：タイマーがまだ残り時間があるうちに押した場合は、残り時間に加算する
- タイマーが0に達した後は**停止せずカウントアップし、超過時間を表示し続ける**（ストップウォッチのような挙動）
- 超過カウントアップ中に「+30秒」「+1分」を押した場合は、超過分に加算するのではなく、**「残り30秒」「残り1分」という新しいカウントダウンとして再スタート**する
- **「+30秒」「+1分」ボタンの長押し**：タイマーの現在状態（未設定／カウントダウン中／超過中のいずれでも）に関わらず、その時間ちょうど（30秒／1分）の新しいタイマーとして即座にスタートする。このときのモード（通常／連動）は、**直前に選んでいたモードを引き継ぐ**（連動タイマーを使っていた直後であれば、長押しで始まる新規タイマーも連動タイマーとして開始する）
- フラッシュ：タイマー完了の5分前・3分前・1分前、および完了ちょうどの瞬間に**単発**フラッシュ（長さはHTML版の点滅1回分。通常のフラッシュ演出＝完了◯分前フラッシュや指定時刻フラッシュはHTML版のストロボ演出の長さのままでよい）。単発フラッシュも3-5節と同じ「演出がちょうどその時刻に終わる」ルールに従う（＝点滅1回分の長さだけ前倒しで開始する）
- タイマーがリセットされた場合（ストップウォッチのリセットに連動する場合を含む）、そのタイマー自身の「発火済みフラッシュ」の記録もクリアする（リセット後は5分前・3分前・1分前・完了ちょうどのフラッシュが再び有効になる）

### 3-2. ストップウォッチのジェスチャー追加
- **ダブルタップ**：経過時間を0にリセットし、即座に再スタートする（＝リスタート）
- （既存の）シングルタップ＝開始／一時停止、長押し＝0にリセットして停止、は維持する

**実装方針：プラットフォーム標準のジェスチャーイベントを優先する**

シングルタップ／ダブルタップ／長押し（タップ＆ホールド）は、採用するフレームワーク（iOS/Android/Flutter/React Native等）に標準のジェスチャー認識イベントが用意されている場合は、それをそのまま使用すること。自前でタイマーを組んで判定するのは、標準イベントが存在しない場合の代替手段とする。

以下は標準イベントが使えない場合のフォールバック用ロジック（参考）：

1. `pointerdown` で長押し判定タイマー（例：600ms）を開始する
2. 600ms経過前に `pointerup` が来た場合、長押しではなく「タップ」として扱う。600ms経過後も指が離れなければ長押し確定＝即座にリセット（停止）を実行する
3. タップと確定したら、即座に開始／一時停止を実行せず、二重タップ判定用の短い待機（例：300ms）を挟む
   - 待機中に2回目の `pointerdown` が来たら「ダブルタップ」と確定し、リセット＋再スタートを実行する
   - 待機時間内に2回目のタップが来なければ「シングルタップ」と確定し、開始／一時停止を実行する
4. この自前実装の場合、シングルタップの反応が待機時間（約300ms）だけ遅延する点に注意。標準イベントを使う場合はこの制約は基本的に発生しない

### 3-3. 完了◯分前フラッシュのデフォルト値
初期状態で以下を自動的にセットしておく（ユーザーが追加/削除でカスタマイズ可能なのは従来どおり）：

```
120分, 90分, 60分, 45分, 30分, 20分, 15分, 10分, 5分, 3分, 2分, 1分
```

### 3-4. フラッシュ残り時間表示のUI刷新
現状は横に並んだチップで全件表示していたが、フラッシュ地点が最大12個に増えるため表示を見直す。

- 画面には**常に3つまで**表示し、他は存在することがわかるように「…」で示す
- **左右スワイプ**で表示する3つを切り替えられる。スワイプアニメーションは滑らかに
- デフォルト表示は「このあと発火する直近3つ」
- ユーザー操作なしで**5秒経過したら自動的にデフォルト位置（直近3つ）へ戻る**

### 3-5. フラッシュ発火タイミングの仕様変更
現行版は「指定時刻ちょうど」に一瞬だけフラッシュしていたが、これを変更する。

- **指定時刻より前からフラッシュを開始し、指定時刻ちょうどでフラッシュが終わる**ようにする
- 発火するフラッシュ自体の長さ（点滅パターン）はHTML版のストロボ演出（6回点滅・合計約3秒）のまま。「何秒前から開始するか」はこの演出の長さに合わせて逆算する（＝フラッシュ終了時刻＝指定時刻になるよう、演出開始時刻を指定時刻から演出の長さ分だけ前倒しする）

### 3-5-1. フラッシュが重複した場合の挙動（新規）
デフォルトで完了◯分前フラッシュが12地点、それに加えて指定時刻・タイマーの単発フラッシュも重なるため、複数のフラッシュ演出がほぼ同時に発火するケースが起こり得る。現行のHTMLプロトタイプはアニメーションクラスの付け替えのみで、後から発火したフラッシュが前のフラッシュを中断・上書きしてしまう。ネイティブアプリでは以下のいずれかの方針で対応することを推奨する：

- 発火タイミングが近い（例：1秒以内）ものは1回のフラッシュにまとめる（合図の意味は変わらないため）
- タイミングが離れているものは、再生中の演出を中断せずキューイングして順番に再生する

いずれの方針を採るかはClaude Code側の実装判断でよいが、「後発のフラッシュで前のフラッシュが見えなくなる」ことだけは避けること。

### 3-6. NTP時刻同期の仕様明確化
- NTP（時刻サーバー）から時刻取得を試み、**取得に成功した場合はアプリ内の全ての時刻計算をNTP時刻基準に切り替える**
- 取得に失敗した場合は端末のシステム時刻にフォールバックする
- **端末のシステム時計自体は変更しない**（NTPで得た時刻はアプリ内部の補正値としてのみ使用）

### 3-7. 完了時刻の永続化
- 設定した「完了時刻」は、アプリを終了しても保持される
- その時刻を過ぎるまでは、アプリを再起動しても完了時刻が設定された状態（カウントダウン中）で復帰する
- アプリを稼働させたまま完了時刻を超過した場合は、これまでどおり「超過」表示を継続する
- **再起動をまたいで、すでに完了時刻を超過していた場合は、未設定状態に戻す**
- 完了時刻に付随する「発火済みフラッシュ」の記録（完了◯分前フラッシュのうちどれが発火済みか）も完了時刻と一緒に保存し、再起動直後に過去分をまとめて発火させないようにする
- 保存する値は「HH:MM」のような時刻文字列ではなく、**絶対時刻（epochミリ秒などのタイムスタンプ）**にすること。日付をまたいだ場合や、NTP補正の有無が再起動時に変わった場合でも、保存済みの完了時刻がずれないようにするため
- ※これはブラウザのHTMLプロトタイプでは実現が難しく、今回ネイティブアプリ化する主な理由のひとつ
- ※完了時刻**以外**のデータ（指定時刻リスト、フラッシュ地点のカスタマイズ、タイマー・ストップウォッチの実行中状態、週末マイルストーン、通知設定など）も同様に再起動をまたいで保持する。それぞれ「時刻・日付が過ぎて超過している場合はリセットする」という考え方は完了時刻と共通とする（詳細は3-8節・3-9節を参照）

### 3-8. 完了時刻以外のデータの永続化（新規）
以下も同様にアプリ終了後・再起動後に保持する：

- 指定時刻リスト（複数の指定時刻）：各指定時刻ごとに、すでにその時刻を超過しているものは再起動時にリストから取り除く。まだ先の時刻のものはそのまま保持する
- フラッシュ地点のカスタマイズ（完了◯分前フラッシュの一覧。デフォルトの12地点から追加/削除した内容）：時刻ではなく「完了◯分前」という相対設定のため、そのまま保持してよい（超過の概念がないため常に保持）
- 週末マイルストーン一覧：**Issue #44で仕様変更**。種別（OR/WE/WD/CR/SS/CS）つきのセッションスケジュール管理に置き換わり、過去の項目もチェーン日数計算に必要なため削除しない（このルールのみ、他の項目とは異なり超過分を取り除かない）。詳細は`plans/feat-session-schedule.md`参照
- 通知のON/OFF設定：常に保持する（超過の概念がないため）

### 3-9. タイマー／ストップウォッチの永続化
- タイマーが動作中（カウントダウン中、または0到達後の超過カウントアップ中）の状態でアプリが終了・再起動された場合も、タイマーの状態（残り時間、モード、超過状態かどうか）を保持し、再起動後もそのまま継続動作させる
- タイマーが未設定（動いていない）状態でアプリを終了した場合は、再起動後も未設定のままでよい
- 完了時刻（3-7節）と異なり、タイマーは「時刻」ではなく「残り秒数」で管理されるため、超過による自動リセットの概念はない（超過してもカウントアップを続けるだけで、その状態自体を保持する）
- **ストップウォッチも同様に永続化する**：計測中（走っている状態）または一時停止中のいずれであっても、アプリ終了・再起動後にそのまま継続動作させる（経過時間を保持し、再起動後も計測中であればカウントを続ける）
- 実装上は、タイマー・ストップウォッチとも「開始基準となる絶対時刻（epoch）＋その時点での累積時間」を保存し、再起動時にその基準から現在時刻との差分を再計算する方式を推奨する（3-7節の完了時刻と同じ考え方）

## 5. 非機能要件（プロトタイプで検証済みの方針を継続）

- **電池消費**：長時間（3〜4時間以上）画面点灯を想定。有機EL想定の黒背景、再描画の最小化、画面スリープ抑止（Wake Lock相当の機能）
- **バックグラウンド／画面ロック時の動作**：基本利用シーンは画面をつけっぱなしにする運用だが、OSの省電力機能や誤操作で画面が消える可能性はゼロではない。フラッシュ演出はアプリがフォアグラウンドにある前提でよいが、**通知だけはOSのローカル通知スケジューリング機能を使い、画面が消えていてもフラッシュ予定時刻に発火する**ようにしておくと運用上の保険になる
- **オフライン動作**：NTP同期以外の主要機能（完了時刻カウントダウン、指定時刻カウントダウン、ストップウォッチ、タイマー、フラッシュ、通知）はネット接続なしで動作すること
- **タイムゾーン**：端末設定に準拠（日本国内利用が主だが、端末側の設定を正としてハードコードしない）
